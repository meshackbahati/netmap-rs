    netmap-rs · version 0.3.1

    Kernel-Bypass Networking in Rust

    netmap-rs provides safe, zero-cost abstractions for Netmap kernel-bypass networking in Rust. Netmap exposes packet buffers as memory-mapped ring buffers shared with the kernel, which removes per-packet copies and system-call overhead and which makes high-throughput, low-latency packet processing attainable from ordinary user space.

    This documentation describes the crate as it stands at version 0.3.1, which migrated to the Netmap 14 API through netmap-min-sys 0.3.1. It is organised as a sequence of short sections that may be read in order or consulted by topic, since each section states its prerequisites at the outset.

    How to use this documentation. Use the contents list to move between sections; the previous and next buttons at the foot of each section preserve the suggested order. Interactive examples, which are marked with the heading “Try it”, run entirely in the browser and require neither a Netmap installation nor compilation of the crate.

    Orientation and Repository Map

    This section situates the crate within its repository so that later sections can refer to files by name without ambiguity. The figures below reflect version 0.3.1, which contains roughly 6,300 lines across sources, examples, applications, tests, and documentation.

    What the crate is

    netmap-rs is a safe Rust wrapper over the Netmap C framework. The unsafe foreign-function interface is confined to the netmap-min-sys dependency and to small, audited unsafe blocks inside src/netmap.rs, src/ring.rs, and src/tokio_async.rs. Everything else, including error handling, packet views, and the fallback channel, is safe Rust which the compiler checks.

    Section 2 · Prerequisites: Section 1

    Installation and Configuration

    Most users need two things: the Netmap C library on the build machine, and the sys feature enabled in Cargo.toml. This section treats each in turn, then provides an exercise that generates the correct dependency snippet.

    Installing the Netmap C library

    On FreeBSD 11 and later, Netmap ships with the base system and no installation is required. On Linux, build and install the module from the upstream repository, then load it:

    $ sudo apt-get install build-essential git linux-headers-$(uname -r)
$ git clone https://github.com/luigirizzo/netmap.git
$ cd netmap/LINUX && ./configure && make && sudo make install
$ sudo insmod netmap.ko
$ ls /dev/netmap   # confirms the device node exists

    A convenience script is also provided at scripts/install_netmap.sh. If Netmap lives in a non-standard prefix, export NETMAP_LOCATION before building, since build.rs searches $NETMAP_LOCATION/include/net/netmap_user.h and links libnetmap from $NETMAP_LOCATION/lib:

    $ export NETMAP_LOCATION=/opt/netmap
$ cargo build --features sys

    Adding the crate

    For ordinary synchronous use, enable sys. For Tokio integration, add tokio-async as well:

    $ cargo add netmap-rs --features sys
# with async support:
$ cargo add netmap-rs --features sys,tokio-async

    Try it: generate your dependency snippet

    Select the capabilities your project needs; the snippet updates accordingly.



    [dependencies]
netmap-rs = { version = "0.3", features = ["sys"] }

    Section 3 · Prerequisites: Sections 1–2

    Core Concepts: Rings and Names

    Netmap models each network interface as a set of independent rings. A transmission (TX) ring carries packets from the application to the wire, while a reception (RX) ring carries packets from the wire to the application. Each ring is a fixed-size circular array of slots, and three indices govern it: head, which marks the next slot to use; tail, which marks the kernel’s position; and cur, which tracks the application’s cursor and which in this crate follows head after every operation.

    The direction-aware contract

    Since 0.3.1, synchronisation is direction-aware: Ring::sync() issues NIOCTXSYNC for TX rings and NIOCRXSYNC for RX rings. On RX rings, received packets occupy the half-open range [head, tail) and are read starting at head, after which head advances. A TX ring is full when (head + 1) % num_slots == tail, and attempting to send into a full ring yields Error::InsufficientSpace (or WouldBlock in the fallback channel).

    This simulator models an 8-slot TX ring with the same fullness rule as the crate. Send packets, then run a kernel drain (sync) to free slots.

    Section 4 · Prerequisites: Section 3

    Guided Tour of the Modules

    The crate exposes six modules. The table below summarises each, after which the sections that follow state the exact items a reader must know.

    error: one enum for all failures

    Error has eight variants: Io, WouldBlock, BindFail(String), InvalidRingIndex(usize), PacketTooLarge(usize), InsufficientSpace, UnsupportedPlatform(String), and FallbackUnsupported(String). It converts into std::io::Error, which is what allows the async wrappers to satisfy Tokio’s AsyncRead and AsyncWrite contracts.

    frame: the packet view

    Frame<'a> wraps a Cow<'a, [u8]>: frames received from a live ring borrow the shared buffer without copying, while fallback frames own their bytes. Construction is via Frame::new (borrowed), Frame::new_borrowed (an alias), Frame::new_owned, or From<&[u8]>. Inspection is via len, is_empty, and payload, and Frame additionally dereferences to [u8].

    netmap: opening interfaces

    ItemBehaviour
    NetmapBuilder::new(name)Parses netmap: prefixes, ^ host suffixes, and pipe names
    .num_tx_rings(n) / .num_rx_rings(n)Requested ring counts; 0 means “all available” (1 by default on pipes)
    .flags(f)ORs operational nr_flags with internally derived registration flags
    .build()Calls nm_open; reports the actual ring counts from the descriptor
    Netmap::tx_ring(i) / rx_ring(i)Ring handles; out-of-range indices yield InvalidRingIndex
    num_tx_rings, num_rx_rings, is_host_ifIntrospection of the opened interface

    ring: moving packets

    ItemBehaviour
    Ring::index, num_slots, head, tail, dir, direction, has_free_slotsIntrospection; direction() returns the typed RingDirection::Tx or Rx
    Ring::syncDirection-aware ioctl (NIOCTXSYNC vs NIOCRXSYNC)
    TxRing::sendCopies one packet into the slot at cur; rejects oversize payloads
    TxRing::reserve_batch(n)Checks n free slots, else InsufficientSpace
    BatchReservation::packet(i, len) + commit()Zero-copy fill of each reserved slot, then a single head advance
    RxRing::recv / recv_batchReads at head and advances it; returns None / 0 when empty

    fallback, tokio_async, and the re-exports

    fallback offers FallbackTxRing, FallbackRxRing, and create_fallback_channel(max_size), which share one bounded queue behind an Arc<Mutex<…>>; a full queue reports WouldBlock. These are examined in Section 9. tokio_async provides TokioNetmap, AsyncNetmapRxRing, and AsyncNetmapTxRing and is examined in Section 8. Finally, the crate root re-exports the raw bindings as ffi and gathers the everyday types (Error, Frame, and, under sys, Netmap, NetmapBuilder, Ring, RxRing, TxRing) into prelude.

    Section 5 · Prerequisites: Sections 3–4

    Basic Usage: Send and Receive

    The canonical program opens an interface, takes one TX and one RX handle, sends a packet, synchronises, and polls for its return. Three equivalent framings follow: synchronous Netmap, asynchronous Tokio, and the dependency-free fallback.

    use netmap_rs::prelude::*;
use std::thread::sleep;
use std::time::Duration;

fn main() -> Result<(), Error> {
    let nm = NetmapBuilder::new("eth0")
        .num_tx_rings(1)
        .num_rx_rings(1)
        .build()?;

    let mut tx_ring = nm.tx_ring(0)?;
    let mut rx_ring = nm.rx_ring(0)?;

    let packet_data = b"hello netmap!";
    tx_ring.send(packet_data)?;
    tx_ring.sync(); // hand the packet to the hardware

    for _ in 0..5 {
        rx_ring.sync(); // publish consumed slots, observe arrivals
        while let Some(frame) = rx_ring.recv() {
            println!("Received: {:?}", frame.payload());
            return Ok(());
        }
        sleep(Duration::from_millis(100));
    }
    eprintln!("No packet returned; check the interface setup.");
    Ok(())
}
    use netmap_rs::NetmapBuilder;
use netmap_rs::tokio_async::TokioNetmap;
use tokio::io::{AsyncReadExt, AsyncWriteExt};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let nm = NetmapBuilder::new("netmap:pipe{example}").build()?;
    let tokio_nm = TokioNetmap::new(nm)?;

    let mut tx = tokio_nm.tx_ring(0)?;
    let mut rx = tokio_nm.rx_ring(0)?;

    tx.write_all(b"hello async netmap").await?;
    tx.flush().await?; // performs NIOCTXSYNC

    let mut buf = [0u8; 2048];
    let n = rx.read(&mut buf).await?; // performs NIOCRXSYNC
    println!("Received: {:?}", &buf[..n]);
    Ok(())
}
    use netmap_rs::fallback::create_fallback_channel;

fn main() {
    let (tx, rx) = create_fallback_channel(64);
    tx.send(b"hello fallback").unwrap();
    if let Some(frame) = rx.recv() {
        assert_eq!(frame.payload(), b"hello fallback");
    }
}
    Audit note. An earlier version of this page showed a Tokio example calling TokioNetmap::new("eth0").await, which does not exist. The corrected sequence above (build a Netmap first, wrap it with TokioNetmap::new, then take ring handles) matches src/tokio_async.rs.

    The Applications Catalogue

    The apps/ directory mirrors the layout of the upstream Netmap C repository and holds five ready-to-run binaries. All require sys (hence the kernel module), yet all operate exclusively on VALE ports and pipes, so none disturbs a live network interface.

    Section 8 · Prerequisites: Sections 3–5

    Asynchronous I/O with Tokio

    Under the tokio-async feature, TokioNetmap wraps a Netmap instance’s file descriptor in tokio::io::unix::AsyncFd so that ring operations participate in the Tokio reactor instead of blocking a thread.

    The three types

    • TokioNetmap::new(netmap) registers the descriptor; rx_ring(i) and tx_ring(i) validate the index and capture a raw ring pointer tied to the shared AsyncFd.
    • AsyncNetmapRxRing implements AsyncRead. Each poll_read first issues NIOCRXSYNC so arrivals become visible, copies one packet into the caller’s buffer, advances head, and otherwise parks the task until the descriptor reads ready.
    • AsyncNetmapTxRing implements AsyncWrite. poll_write copies one packet into a free slot (parking the task when the ring is full), while poll_flush and poll_shutdown issue NIOCTXSYNC to hand queued packets to the kernel.
    Correctness point. The sync calls are not optional conveniences; without the RX sync the reader would never observe traffic, and without the TX sync on flush nothing written would reach the kernel. The wrappers therefore perform them on every relevant poll.

    See examples/tokio_pipe_async.rs and apps/tokio-proxy for complete programs, and note that the 0.3.1 history records a fix to poll_read so that it reads at ring.head rather than a stale offset.

    Section 9 · Prerequisites: Section 4

    Fallback Mode Without Netmap

    On machines where Netmap is unavailable (continuous-integration runners, for instance), the crate still builds without the sys feature, exposing Error, Frame, and the fallback channel. create_fallback_channel(max) returns a connected (FallbackTxRing, FallbackRxRing) pair over a shared bounded queue: send copies into the queue and reports WouldBlock when full, while recv pops owned frames in FIFO order.

    The fallback is a behavioural stand-in rather than a performance equivalent. It preserves the send/receive shape of the API so that protocol logic above the rings can be developed and unit tested anywhere, while any timing or throughput claim must still be validated against real rings as described in Sections 10 and 11.

    Section 10 · Prerequisites: Sections 3–7

    Performance: Threads, Batches, and Benches

    Throughput in this crate comes from three compounding choices: dedicating threads to rings, amortising synchronisation with batches, and measuring with Criterion.

    Thread-per-ring

    Because each ring handle is Send, a program may hand every TX and RX ring to its own thread and pin each thread to a core with core_affinity. The thread_per_ring example shows the pattern: open N rings of each direction, spawn one thread per handle, and join them. Consult NUMA topology when choosing the pinning so that rings serving the same interface share a socket where possible.

    Batch reservations

    Where send copies one packet and advances head immediately, reserve_batch(n) first verifies that n slots are free, then hands out &mut [u8] slices for direct filling via packet(i, len), and finally commit() advances head once for the whole batch. The pkt-gen app’s -b flag exercises exactly this path.

    Benches

    benches/latency.rs measures single-packet round-trip cost and benches/throughput.rs measures sustained transfer, both through Criterion:

    $ cargo bench --features sys --bench latency
$ cargo bench --features sys --bench throughput

    Section 11 · Prerequisites: Sections 2–3

    The Virtual Lab and Test Suite

    No physical NIC is needed to learn or verify this crate. Netmap provides two purely virtual, in-memory port kinds: VALE ports (vale0:name), which behave as ports on an in-kernel Ethernet switch and which enforce the 14-byte Ethernet minimum frame size; and Netmap pipes (pipe{name master, pipe}name slave), which form a bidirectional channel between two endpoints. Opening either registers it on demand, so the canonical first experiment is:

    $ cargo run --example ping_pong --features sys

    Test suite map

    SuiteScope
    Unit tests in src/Frame semantics, error display strings, fallback FIFO and fullness, From conversions, Send + Sync bounds
    tests/mock.rsFallback ring behaviour without Netmap
    tests/tests.rsUpdated API surface checks
    tests/integration.rsEnd-to-end VALE and pipe flows; parallel-safe via unique port names per test

    Host-ring tests against interfaces such as netmap:lo^ are gated behind NETMAP_TEST_HOST_RINGS=1, so the default suite never touches loopback or any live NIC:

    $ cargo test --features sys
$ NETMAP_TEST_HOST_RINGS=1 cargo test --features sys  # opts into host-ring tests

    Frequently asked questions

    Must I disturb production interfaces to experiment? No. VALE ports and pipes are virtual and isolated; see Section 11.

    Why does recv return None right after a send? Because each side needs its sync: TX sync hands packets to the kernel, RX sync publishes consumed slots and observes arrivals. The loop in Section 5 shows the rhythm.

    Where is the generated API reference? On docs.rs/netmap-rs, which complements but does not replace this narrative guide.
